# 健康生活应用总计划

## 1. 产品目标

做一个个人优先、手机优先的饮食与运动记录网页：尽量降低记录摩擦，帮助用户形成可持续的热量缺口，同时保留人工修正权。它不是诊疗工具，不根据单张照片假装给出精确营养值，也不把模型估算当成医学事实。

首版成功标准：用户能在一分钟内完成初始档案；能用文字记录一餐、手动修正估算并保存；能记录运动与体重；首页能看见当天摄入、运动、预算余量和近七日趋势；能把食材分为绝不吃、不爱但可吃、可接受、喜欢四档；能据此生成一日三餐建议。

## 2. 产品原则

1. **估算必须可见、可改。** 每条自动结果展示区间、置信度和依据；最终保存前允许改份量与热量。
2. **热量缺口不是越大越好。** 根据档案给出保守默认值，并在目标过激、BMI 偏低、每日预算异常时提醒咨询专业人士。
3. **模型负责识别，规则负责计算。** 图片或自然语言由模型拆成食物候选；营养值优先查数据库并按克数计算，模型只在数据缺失时给区间。
4. **偏好与禁忌分开。** 过敏、宗教/医学禁忌是硬约束；“不爱但能吃”是低权重；喜欢不是无限重复。
5. **本地优先和数据最小化。** 原始健康记录保存在用户自己的数据目录；图片默认不长期保存，调用远端模型前明确提示会上传。
6. **能离线记录。** 没有模型或营养数据库时仍可手输名称、份量、热量与运动消耗。

## 3. 需求范围

### 3.1 初始档案与目标

- 基础字段：出生年份、身高、当前体重、目标体重、用于代谢估算的生理性别、日常活动等级。
- 可选字段：腰围、目标日期、每周运动安排、疾病/孕哺/饮食失调风险提示。
- 计算并解释：BMI、基础代谢 BMR、日总消耗 TDEE、建议每日摄入、计划热量缺口。
- BMR 首版采用 Mifflin–St Jeor 公式；TDEE 使用活动系数。所有结果明确为估算，运动消耗不默认 100%“吃回来”。
- 每次体重更新后只平滑调整预算，避免单日波动造成剧烈变化。

### 3.2 饮食记录

- 快速文字：如“午饭一碗米饭、番茄炒蛋、半杯奶茶”。
- 手动明细：食物名、份量、单位、热量、蛋白质、碳水、脂肪、纤维。
- 图片：拍照/上传后返回食物候选、估计份量、热量区间和待确认问题；用户确认后才入账。
- 包装食品：后续支持条码查 Open Food Facts；常见天然食物与菜品优先使用本地收藏和 USDA/地区数据库。
- 支持餐别、时间、备注、饥饿感/饱腹感；允许编辑和删除。

### 3.3 运动与身体记录

- 手动记录运动名称、时长、估计/设备给出的热量消耗、强度和备注。
- 快捷运动模板；后续可按 MET × 体重 × 时长估算。
- 体重按日期记录；首页显示七日移动平均，避免被水分波动误导。
- 后续可接 Apple Health / Health Connect，但首版不做平台原生权限集成。

### 3.4 食材偏好与食谱规划

- 分类：蔬菜、水果、主食、豆类、蛋奶、肉禽、海鲜、坚果、调味品、其他。
- 四档喜好：`avoid` 绝不吃、`reluctant` 不爱但勉强可吃、`neutral` 可接受、`love` 喜欢。
- 硬约束另存：过敏、宗教/伦理、医嘱、烹饪设备、做饭时长、预算。
- 菜谱包含食材克数、做法、估算营养、替换选项；推荐必须解释如何满足热量和偏好。
- 一日计划先用确定性配额分配早餐/午餐/晚餐/加餐预算，再由模板或模型选菜，最后由规则校验总热量、蛋白质、蔬果多样性和硬约束。
- 用户可把建议标成喜欢/不喜欢，作为以后排序信号，不自动更改硬约束。

### 3.5 首页与反馈

- 今日圆环/条形进度：摄入、基础预算、运动、净余量。
- 三大营养素与纤维概览；缺数据时显示“未记录”，不显示误导性的 0。
- 最近七日：体重趋势、平均摄入、平均缺口、记录完整度。
- 提示语聚焦下一步行动，不用羞辱性红字，不用“失败/作弊餐”等措辞。

## 4. 技术架构

首版沿用仓库约束：Python 3.12 标准库 + 原生 HTML/CSS/JavaScript，不增加包。健康应用作为独立模块运行，避免和夜班任务状态、登录页面及 API 混在一起。

```text
手机浏览器
   │ HTTPS（由现有反向代理负责）
   ▼
wellness HTTP 服务
   ├── 静态页面 /health/
   ├── JSON API /health/api/*
   ├── 原子 JSON 数据仓库 + 文件锁
   ├── 纯函数：BMR/TDEE/目标与汇总
   └── 可插拔估算器
         ├── local：离线关键词/用户确认
         └── openai：图片/文本拆解（后续启用）
```

建议目录：

- `nightshift/wellness.py`：命令入口、HTTP 路由和输入校验。
- `nightshift/wellness_store.py`：用户档案、记录、偏好和计划的原子持久化。
- `nightshift/wellness_calc.py`：代谢、预算、每日汇总和安全边界纯函数。
- `wellness/index.html`、`wellness/app.js`、`wellness/style.css`：独立手机网页。
- `tests/test_wellness_*.py`：纯函数、存储、API 和静态页测试。

数据存放在 `$NIGHTSHIFT_HOME/wellness/`。每类资源使用 JSON 文档；写入必须先写同目录临时文件、`fsync` 后 `os.replace`，读改写使用独立锁文件的 `fcntl.flock`，避免并发请求丢数据。图片放临时文件，默认在估算完成后删除。

### 4.1 首版数据模型

- `profile.json`：版本、档案、目标、计算偏好、更新时间。
- `entries/YYYY-MM-DD.json`：当天 meals、exercises、weight、water；记录有 UUID、时间、来源、估算区间、用户是否确认。
- `preferences.json`：按分类保存食材和四档偏好，另有 allergies、dietary_rules、equipment。
- `plans/YYYY-MM-DD.json`：生成参数、各餐方案、营养汇总、替换项和用户反馈。

API 使用稳定 envelope：成功为 `{ok: true, data: ...}`，失败为 `{ok: false, error: {code, message, fields?}}`。所有写接口限制正文大小、拒绝未知类型、校验日期和有限数值；网页输出使用 `textContent`，不把用户输入拼成 HTML。

## 5. 模型和食物数据方案

### 5.1 为什么照片需要模型，但不能只靠模型

单张照片缺少重量、油量、酱料和被遮挡内容，无法可靠得出精确热量。正确流程是：视觉模型识别候选食物和大致体积 → 对低置信结果提问 → 用户确认份量 → 查营养数据库 → 规则计算总量。结果应给区间，例如 520–760 kcal，而不是伪精确的 613 kcal。

OpenAI Responses API 支持文字/图片输入和 JSON 输出；后续适配器应要求严格结构化结果，并设置 `store: false`，服务端读取密钥，绝不能把 key 发到浏览器。开发和 CI 使用固定假响应，不做真实调用。参考：[OpenAI Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)。

### 5.2 数据源

- 常见食材：USDA FoodData Central 提供搜索和详情 API，数据可用于营养计算；正式使用需把 data.gov key 放在数据目录配置里，仓库不保存。参考：[FoodData Central API Guide](https://fdc.nal.usda.gov/api-guide/)。
- 包装食品：Open Food Facts 可按条码获取营养信息，但数据由社区维护，必须显示来源并允许纠错。参考：[Open Food Facts API](https://openfoodfacts.github.io/openfoodfacts-server/api/)。
- 中式复合菜：首版先做用户自定义常用菜模板；后续再评估权威地区数据集。模型猜测只能作为待确认草稿。
- 体重目标：更完整的动态预测可参考 NIH Body Weight Planner；首版先做透明的静态估算和保守护栏。参考：[NIDDK Body Weight Planner](https://www.niddk.nih.gov/bwp)。

### 5.3 模型输出契约（后续）

输入包含图片、用户文字、餐别和可选参照物；输出只允许：`items[]`（名称、估计克数区间、候选查询词、置信度、依据）、`questions[]`、`overall_confidence`。模型不得直接决定日目标、诊断疾病或绕过用户确认写入正式记录。

## 6. 安全与隐私

- 明示这是生活记录与估算工具，不替代医生/营养师；未成年人、孕哺期、进食障碍史、慢性病或药物影响者不使用自动减重预算。
- 对异常目标给软阻断：目标 BMI 过低、期限过短或预算低于配置下限时不自动生成减重计划，只展示维护热量并建议寻求专业意见。
- 默认单用户部署，仍需沿用口令/cookie 或反向代理鉴权；所有改变状态的请求校验同源与 CSRF token。
- 健康数据不写日志；异常日志不包含请求正文、图片和档案。
- 提供 JSON 导出与“一键删除健康数据”；删除操作必须二次确认并采用可恢复策略或明确说明不可恢复。

## 7. 分期施工

### M0：本班可交付骨架

- 独立 `/health/` 移动端页面。
- 档案与热量目标计算。
- 饮食、运动、体重的手动记录和当日汇总。
- 四档食材偏好编辑。
- 本地规则生成一日餐单草案。
- 原子 JSON 存储、输入校验、专项测试、示例配置和使用说明。

### M1：低摩擦输入

- 中文自然语言记录解析的模型适配器和 mock。
- 照片上传、压缩、结构化识别、确认页和估算区间。
- USDA 搜索缓存、条码查询、常用菜模板与数据来源标记。

### M2：长期效果

- 周/月趋势、记录完整度、体重移动平均。
- 菜单轮换、采购清单、剩菜复用和预算约束。
- 计划与实际对比；从显式反馈学习排序权重。
- 数据导入导出、备份与删除。

### M3：设备与平台

- PWA 离线队列与相机体验。
- Apple Health / Health Connect 同步适配层。
- 多用户账户、端到端备份加密（仅在确实需要共享部署时）。

## 8. 首版验收清单

- 新数据目录启动时不需要手工建文件，且仓库中没有个人信息或密钥。
- 档案计算有正常值、边界值和拒绝危险目标的测试。
- 两个并发写请求不会互相覆盖；损坏 JSON 返回可理解错误且不静默清空。
- 创建、编辑、删除饮食/运动/体重记录后，当日汇总一致。
- `avoid` 和过敏食材绝不会进入计划；`love` 只提高优先级；菜单热量落在目标容差内。
- 未配置模型时文字/手动记录仍完整可用；测试不联网、不发真实模型请求。
- 手机窄屏可完成所有核心动作，键盘操作有可见焦点，表单错误能定位到字段。

## 9. 明确不在首版做的事

- 不承诺照片热量“准确识别”；不做疾病诊断、处方、药物建议或极低热量饮食。
- 不抓取来路不明的食谱站，不把版权菜谱整段存入仓库。
- 不在浏览器保存 API key，不上传未确认的长期健康历史给模型。
- 不在本班接入付费模型、第三方包、原生 iOS/Android 工程或真实可穿戴设备。
